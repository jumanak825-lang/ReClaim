# 11. Work Split — 2-Person Hackathon Build

**Team:** Person A = Backend (FastAPI, PostgreSQL, worker, PayPal, Zapier).
Person B = Frontend (Next.js, UI, AG Grid, end-to-end tests, demo).
**Timebox:** 3 days. **Goal:** the MVP acceptance scenario in
`01_PRODUCT_REQUIREMENTS.md` §1.12 works end to end, repeatably, from a
reset seed.

Status: planning only. Nothing is built yet.

---

## 1. Decisions already made

- Auth: short-lived server-side sessions stored in Postgres, HttpOnly cookie,
  rotated on login, revocable on logout. Next.js proxies `/api/*` to FastAPI
  so the browser sees one origin.
- Local Postgres runs in Docker Compose.
- Spec fixes (record in docs as assumptions):
  - `found_reports` gains `found_location_text`, `found_lat`, `found_lng`
    for individual finders.
  - Recovery states gain `in_transit` between `dispatched` and `received`.
- Package manager: npm. Layout: `apps/api`, `apps/web`.
- AI provider: xAI Grok API (vision + JSON-schema structured output), behind
  the provider interface (`AI_PROVIDER`, `AI_API_KEY`, model id in env). The
  deterministic fallback must work with the key unset.
- PayPal webhook: ngrok free tier with its static domain, run from a laptop
  (no Render deploy for the hackathon). Register the webhook once against
  that domain.
- Demo currency: USD. Sandbox business account created as a US account.

## 2. Hackathon scope

**In** (MVP must-haves, built thin but real):
- Register, sign in, sign out.
- Seeded organisations, locations and staff memberships.
- Lost and found report wizards with image upload.
- AI-assisted extraction, plus a deterministic fallback.
- Matcher with ranked, explained candidates.
- Claim with private questions and evidence.
- Human review with a reason and an audit entry.
- Collection with a one-time pickup token.
- Delivery with a quote, PayPal Sandbox checkout, server-side capture and a
  verified webhook.
- Simulated courier, clearly labelled.
- 2 Zapier automations via signed outbox events.
- AG Grid operations table.
- In-app notifications.
- Seed and reset script.

**Cut or stubbed for the hackathon** (listed so nobody builds them):
- Password reset and email verification. Show a "not available in demo" note.
- Email notifications. In-app only.
- Organisation, location and member management UI. Seeded data only.
- Per-organisation integrations settings UI. A single Zapier endpoint comes
  from env config, shown read-only with a "Send test event" button.
- Finder payouts, maps, CSV export, admin area, refunds UI.
- QR code rendering. Show the pickup token as text; add QR only if time is
  left.
- Image embeddings. The visual-similarity weight is redistributed as
  §6.5 allows.

## 4. How you work in parallel

1. **Hour 0–2, together:** agree on the endpoint list and the DTO shapes for
   the demo path (§5 below), using `05_API_CONTRACTS.md` as the base. A
   commits FastAPI route stubs with Pydantic schemas that return fixture
   data, so `/openapi.json` exists from the start.
2. B builds against those stubs straight away. A replaces stub bodies with
   real logic without changing the schemas. Any schema change needs a message
   to B before merging.
3. Use one short-lived branch and PR per feature. Merge to `main` at least
   twice a day. The other person reviews any PR touching auth, permissions
   or payments.

## 7. Open risks — decide early

1. **Grok model id and price.** Confirm the current vision-capable model and
   its pricing on docs.x.ai before Day 2; third-party sources disagree.
2. **Tunnel URL stability.** If the tunnel URL changes, re-register the PayPal
   webhook. Only PayPal calls in; Zapier is outbound.
3. **Backend load.** A carries more work. If A falls behind on Day 2,
   B takes notifications or the cases list API, coordinating first.
